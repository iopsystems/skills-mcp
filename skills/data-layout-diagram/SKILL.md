# Data layout diagrams

A layout figure answers a question prose answers badly: **what occupies which
bytes, and what points at what.** Prose carries a sequence; a layout is a shape
with addresses, and re-deriving it from sentences is the work the figure exists
to remove.

This skill owns layout. `architecture-diagram` owns what exists and what
contains what; `dataflow-diagram` owns what moves where. When the question is
"which byte is that field in", it is this one.

## What this is, and what it is not yet

Treat this skill as **beta**. Its conventions were derived from one binary
format in one repository — an encoded list block with a fixed header,
variable-width entries, and a reserved chaining scheme. The provenance rules
below are the transferable part and the visual defaults are the least tested.
Adopt them wholesale, and when one fights your format, the override and its
reason are the most valuable thing the effort produces: record it through
`engineering-journal`.

## Provenance decides what a figure may assert

Every layout figure is one of three things, and its source file says which in
its first line. This is the rule the rest of the skill rests on, because a
reader cannot tell a measured figure from an imagined one by looking.

**Derived by the implementation.** A program in the repository walks a real
instance using the production decoder and emits the figure. The header says so
and says the command:

<!-- cite-ignore -->
```
// GENERATED by `cargo run -p ziplist --example block_anatomy` — do not edit.
// Derived from tests/golden.rs::hash_golden_bytes via the crate's own decoder.
```

This figure asserts what the code does. It cannot disagree with the decoder,
because it is the decoder — which is also its limit: a decoder bug is drawn
faithfully.

**Derived by an independent decoder.** A separate program re-implements the
format from its specification, walks the same frozen bytes, and **aborts** when
its reading and the bytes disagree. This figure asserts what the specification
says, and the mismatch it catches is exactly the one the first kind cannot: an
implementation that has drifted from its own documented format.

Both kinds beat a hand-drawn grid, and a format worth two decoders is worth
both figures.

**Hand-authored schematic.** A claim about design rather than about bytes:
variant conventions, a reserved shape, a comparison of what ships against what
is planned. It says so in its header and names what is not built:

<!-- cite-ignore -->
```
// Hand-authored schematic (a design claim, not derivable from code):
// v1 as shipped vs. the v2 chained shape reserved by the chain-root flag.
// Dashed = reserved-not-built.
```

A schematic may draw what does not exist. A derived figure may not. Mixing the
two in one picture without marking which half is which is the failure this
section exists to prevent.

## The derivation contract

A derived figure is generated by a program that fails loudly rather than
drawing something plausible:

- **Abort on any disagreement.** Every span the figure draws is checked against
  the bytes it claims to describe. A length that does not match, a count that
  does not match the walk, a pointer that does not land on the element it names
  — each aborts with what disagreed. A figure that renders is a figure whose
  claims held.
- **Check the frame, not only the content.** Cells that overflow the drawing
  bounds are a failure, not a cosmetic problem: a figure that silently clips is
  worse than one that refuses to render.
- **Freeze the instance.** Draw a fixture the tests already pin, not a fresh
  encoding. Name the fixture and the commit it was frozen at, in the script
  header and in the prose that carries the figure.
- **State the regeneration command** in the script's own header, so the next
  person changes the generator rather than the output.

The instance is chosen for coverage, not for size: the smallest encoding that
exercises the header, at least two entries, at least two width tiers, and every
cross-reference the format defines. A figure of a one-entry block teaches the
header and nothing else.

## The three charts

**Byte anatomy** — one encoded instance, one cell per byte, in offset order.
This is the chart that must be derived. It carries: the value of every byte, an
offset ruler beneath, brackets naming each span above, and an arrow for every
stored offset that points at what it addresses. The arrow is the part readers
remember, because it turns a number in a header into a place in the picture.

**Variant conventions** — the same encoding arranged as each variant uses it,
one row per variant. Schematic. It shows what the byte anatomy cannot: that one
variant's entries are positional, another's are ordered pairs, a third's are
sorted by a key the encoding does not distinguish. The rows share a glyph
vocabulary so the reader compares arrangements rather than notations.

**Linkage** — what addresses what, across instances. Schematic. Shipped and
reserved shapes belong in one picture only when the reserved half is visually
distinct, and the caption states which is which.

Most formats need the first. A format with variants earns the second. A format
with more than one block earns the third.

## A default visual language

Adopt wholesale; override with a reason.

- **One cell per byte**, fixed width, in offset order, with the value in hex.
  Bytes are the unit even when fields are wider, because the reader's question
  is "which byte".
- **Fill by role, not by field.** Header, tag, payload, and trailer take four
  fills, and every entry reuses them. The reader learns four colors once
  instead of one per field.
- **A pastel fill with fixed dark ink**, chosen so the roles stay separable
  without relying on hue alone.
- **An offset ruler under the cells**, at reduced opacity. It is a reference
  the eye returns to, not content.
- **Brackets above for spans**, on staggered rows when labels would collide.
  A bracket carries the field name and its decoded value, because the value is
  what lets a reader check the figure against the bytes.
- **Dashed for reserved**, solid for shipped. Never the reverse.
- **A caption that states the claim**, not the contents. "The tail offset
  points at the last entry's first byte, so tail access is constant time" earns
  its space; "diagram of a block" does not.

## Rendering for the host that publishes it

A figure that reads locally and fails on the host is a figure nobody sees.

- **Emit a standalone image.** Fixed ink and an opaque ground, not colors
  inherited from a theme: hosts that embed the figure as an image strip the
  page's context, and a theme-aware figure renders as dark ink on dark ground
  for half the readers.
- **Give it a text alternative twice** — an accessible label inside the image,
  and prose beside it that states the same claim. A reader with images
  disabled, and a reader in a diff view, both get the figure's point.
- **Keep it legible at the width the host renders**, which is narrower than the
  authoring canvas. A figure the reader must pan is prose with extra steps.
- **Commit the source and the rendered output together**, and check the output
  is current the way this repository checks its own rendered diagrams.

## Boundaries

`architecture-diagram` owns structure — units, layers, processes, hosts.
`dataflow-diagram` owns movement — pipelines, topologies, a record's path.
This skill owns layout, and the three do not overlap: a reader asking which
byte holds a length is not asking what contains what.

`technical-prose` owns word choice in labels, captions, and the prose beside
the figure, including its default of American spelling. Field names, type
names, and byte values are untouchable: they are names, and a figure that
renames them to read better has stopped describing the format.

`engineering-journal` owns the durable record of why a format is shaped as it
is. A figure carries the shape; the entry carries the argument.

## Known dead ends

- **Drawing the grid by hand from the specification.** It is correct on the day
  it is drawn and wrong at the first encoder change, with nothing to detect the
  drift. Every hand-drawn byte grid in this skill's evidence base was replaced
  by a generated one.
- **One figure for both the shipped and the planned shape, undifferentiated.**
  Readers act on it as though all of it exists.
- **Regenerating from a live encoding rather than a frozen fixture.** The
  figure changes when unrelated code changes, so its diff carries no signal and
  reviewers stop reading it.
- **A generator that draws what it could not verify.** A decoder that guesses
  at an unrecognized tag and renders something plausible produces a figure that
  is wrong in the one place a reader most needs it right.

## Red flags

- A byte grid with no generator, or a generator with no abort path.
- A figure whose header does not say whether it was derived or drawn.
- A derived figure that draws a shape the code does not produce.
- A schematic that omits which half is reserved.
- Offsets in the figure that no longer match the encoder, with nothing that
  would have caught it.
- A fixture that is not the one the tests pin, or a pinned fixture with no
  commit named.
- Cells that overflow the drawing bounds and are silently clipped.
- A figure that inherits its colors from the reader's theme.
- A caption that names the contents instead of stating the claim.
- An instance chosen for being small rather than for covering the header, two
  entries, two width tiers, and every cross-reference.
- A field name rewritten in a label so the figure reads better.
